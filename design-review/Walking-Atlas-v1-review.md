# Walking Atlas v1.0 設計レビュー

作成日: 2026-11-12  
段階: 設計案。サイト改修、経路リビルド、現地確認は未実施。

## 1. 結論と判断境界

**推奨:** 既存の静的サイトと Leaflet を維持し、清澄白河を含む代表3コースだけを新しいデータ形式と画面で試す。経路は事前計算し、検証状態に応じて表示を制限する。PoCの受け入れ後に既存97件へ段階的に広げる。

この設計で優先するのは、景観を楽しめる道の根拠、歩く経路と距離の一致、個人と歩行会の条件の分離、そして未確認情報の明示である。掲載済み経路をそのまま「良い散歩道」や「現地確認済み」とは扱わない。

### 現行資産の再利用と制約

- 再利用: Leaflet、圧縮ポリラインのデコード、Valhalla／BRouterによる事前計算、標高生成、旧ID・アンカー、旧カード本文、季節データ、ライト／ダーク切替。
- 監査してから使用: `waypoints-raw.json` の座標精度、`ROUTE_GEOM` の形状、`targets.json` の手入力距離、標高の古さ、既存の分岐案、検索・おすすめの判定。
- そのまま使わない: 過去の一括修正専用スクリプト。`Handover.md` §4.4で再利用非推奨とされている。
- 現在の距離ゲートでは、同一道路の往復、見どころの通過、現地の歩きやすさは保証できない。`Routing-Logic.md` の120m近接指標は道路エッジ重複率と意味が違う。
- `tools/survey-overlap.mjs` の実装は12m近接を数え、`Routing-Logic.md` の説明は120m。さらにスクリプトにこの作業場所の絶対パスが埋め込まれている。PoCでは定義と実装を揃えてから再計測する。
- `Routing-Logic.md` のA/Bは「地図優先／下り回避優先」。新しいA/B/Cは「標準／延長／雨天」。内部値を混ぜない。現行の難易度A〜Fとも分離する。

### 清澄白河No.47での追加確認事項

現在の形状は2026-08-29計算、`route-report.md` は7.13kmで距離ゲートOK。経由点間2.243km、2.759kmなど長い区間があり、本文にある芭蕉記念館・竪川親水公園等が実際の線上にあるかは未検証。標高ファイル上の上り118.6m／下り111.3mは計算値で、平坦性や段差なしの現地保証ではない。旧記録の説明にある「実測」は、保存データではルーター計算値を指している可能性があるため、新UIでは「経路計算」と表記する。

## 3. 提案するデータ構造

静的JSON／GeoJSONを正本とし、表示用のカード・地図・距離・旅程・比較をビルド時に同じIDから生成する。編集用データと配信用ファイルは分ける。GeoJSON座標は`[経度, 緯度]`、既存`SERIES.r`は`[緯度, 経度]`なので変換を明示して検査する。

```text
Course 1 ── n RouteOption ── n JourneyLeg
   │                │               └─ walk_outdoor / walk_indoor / rail
   ├── n Waypoint   ├── n ScenicSegment
   ├── n Evidence   └── n RouteReview
   └── n LegacyRef
```

| エンティティ | 主なフィールド | 不変条件・用途 |
|---|---|---|
| `Course` | `id`, `slug`, `title`, `story`, `region`, `themes`, `seasonality`, `startStationId`, `endStationId`, `legacyRefs[]` | コースIDは不変。旧IDと旧アンカーを複数保持できる。 |
| `RouteOption` | `id`, `courseId`, `routeVariant: standard/extended/rainy`, `routingStrategy: one_stroke/descent_avoid/scenic`, `usageProfiles[]`, `difficulty`, `verificationStatus`, `generatedAt`, `reviewedAt`, `routeReason` | 新A/B/C、旧A/B、難易度を別フィールドへ。1コースに同じ変種の別戦略を複数保持できる。 |
| `JourneyLeg` | `kind`, `order`, `geometryRef?`, `distanceM?`, `exposure`, `fromWaypointId`, `toWaypointId`, `durationMin?` | 徒歩・鉄道・屋内を分ける。徒歩距離は徒歩LineStringの形状から集計し、鉄道距離を足さない。形状なしは距離も`unknown`。 |
| `Waypoint` | `id`, `point`, `kind`, `stayMin`, `facilities[]`, `openingInfo`, `verificationStatus` | Pointとして地図、旅程、Walkで同じ位置を使う。開館情報には確認日を付ける。 |
| `ScenicSegment` | `id`, `geometryRef`, `theme`, `preferredDirection`, `viewpoint`, `whyChosen`, `evidenceIds[]` | 見どころの点だけでなく「歩く価値のある道」を記録。写真の権利情報も参照する。 |
| `Evidence` | `id`, `url`, `sourceType`, `publishedAt?`, `visitedAt?`, `checkedAt`, `claims[]`, `rights`, `confidence`, `unknowns[]` | URLだけでなく、何の主張を支えるか、未確認点を残す。 |
| `RouteReview` | `routeOptionId`, `reviewer`, `date`, `issues[]`, `edgeOverlapM?`, `overlapMethod`, `exceptions[]`, `decision` | 同一道路の再通行を測る。エッジ照合できないときは率を合格扱いしない。 |
| `ProfileAssessment` | `routeOptionId`, `usageProfile`, `grade`, `reasons[]`, `cautions[]`, `accessRef` | 同じ形状に対して個人・グループを別評価。難易度と推奨理由を混同しない。 |
| `AccessAssessment` | `originStationId`, `startStationId`, `endStationId`, `returnViaStationId?`, `railLegs[]`, `checkedAt` | 個人用の既定起点・帰着は豊田駅。東京駅経由は候補として記録し、徒歩距離と鉄道距離を別集計。グループは各参加者のアクセスを別評価。 |

`verificationStatus` は `idea → researched → routed → map_reviewed → field_verified`。状態は**経路オプション単位**で、資料調査済みや距離ゲート通過を現地確認済みに昇格させない。旧データの初回移行では、根拠がない状態は`routed`以下に置き、状態の根拠と移行日時を残す。

生成ファイル案: `data/courses/*.json`、`data/routes/*.geojson`、`data/evidence/*.json`、`data/legacy-map.json`、`data/archive/`。コースと経路の対応・座標順・距離・旧リンクをCIで検査する。公開画面は小さなインデックスを先に読み、詳細形状を選択時に読む方式を試す。97件の大きなHTMLをさらに膨らませない。

グループ評価には現行の10時集合〜16時解散、6km前後、急な下りの回避、休憩・トイレ・途中離脱を初期条件として移す。ただし全員の現在の条件はP0で再確認し、旧本文の数値を無期限の保証にしない。保存・未踏／実施済みはPoCではブラウザ内保存を候補とする。端末間同期は静的サイトだけでは成立しないため、必要性とデータ取り扱いを確認してから別設計にする。

## 5. 清澄白河・深川PoCの計画

**対象:** 旧No.47を資料として保存し、清澄白河駅起点の散歩を作り直す。地図の良し悪しを確認するため、まず清澄庭園周辺・深川の街路を重点調査し、終点駅は景観、歩行方向、中央線への帰路を比較して決める。現時点で新しい駅順・距離・屋内連続区間を確定しない。

1. **ベースライン凍結:** 旧カード・旧経由点・旧形状・7.127kmの計算値をコピーし、ファイルハッシュと旧アンカー`course-47`を記録。本文にある地点が線上にあるかを地図で確認する。
2. **資料調査:** 江東区・公園・文化施設などの公式資料、現地紀行、OSM道路、標高を収集。道の景観方向、歩行しやすさ、施設の営業・料金、写真利用条件を主張単位で記録する。
3. **A標準案:** 5〜6kmを目安に、駅から駅へ自然に進む道を設計。清澄庭園、街並み、文化施設の優先順位をつけ、同じ道の往復を避ける。距離を満たさない場合は理由を記し、無理に延ばさない。
4. **B延長案:** Aの価値を残しつつ別の景観を追加する分岐を検討。7〜8kmは目安。旧No.47の錦糸町側往復延伸をそのまま採用しない。
5. **C雨天案:** 起点到着後に切り替えられるか検証。屋内徒歩、屋外徒歩、鉄道移動、屋外露出を別レグにする。連続屋内歩行と開館条件が確認できない場合は「準備中」。
6. **ルーティング・計測:** Valhalla徒歩→BRouterの既存手順を調査用に使い、生成日時・エンジン・道路データ時点を記録。GeoJSONの形状から徒歩距離を再計算。道路エッジ重複率を試算し、旧120m指標と比較する。
7. **レビュー:** 地図を拡大して水域・施設内・横断地点・階段・道路の方向を確認。少なくとも主要景観区間と重要な出入口は現地で確認し、結果を経路状態に反映する。
8. **画面確認:** PCとスマホでA/B/C、線・カード連動、地図なし表示、GPSなしWalk、キーボード操作、動きの軽減を確認する。

**PoCの提出物:** 旧・新形状の差分地図、各案の距離・重複率・標高・雨天露出、採用／不採用理由、出典と確認日、残る未確認事項、PC・スマホ画面、回帰チェック結果。新A/B/Cの距離や安全性はこの工程が終わるまで`unknown`。

**3コースへ進む条件:** 清澄白河でデータ・地図・画面の一連の流れが成立し、手順を柿の木坂・碑文谷と神楽坂・外濠へ再適用できること。3件のPoCを受け入れるまで97件の一括移行はしない。

## 6. 移行方式、工数、費用、リスク

### 段階移行の手順

1. **P0:** 公開元を読み取り確認し、現行HTMLと全生成データのバックアップを作成。97 ID・旧アンカー・旧URL・既知の不整合を一覧にする。元ファイルのハッシュを保存する。
2. **P1:** 新スキーマと旧→新変換器を作る。旧カード・形状・距離・分岐戦略は`legacy`として残し、確証のない値を`unknown`にする。
3. **P2:** 清澄白河で手順を確立し、柿の木坂・碑文谷、神楽坂・外濠へ適用。A/B/Cを資料・地図・現地の各段階でレビューする。
4. **P3:** 代表3件だけを新UIで試し、旧リンクと既存の97件の表示が壊れないことを確認する。
5. **P4以降:** 採用したコースから段階的に切り替える。旧資料・旧形状・変更理由はアーカイブに残す。

| A. 静的JSON＋既存Leafletを段階的に分離 | 既存の地図・経路生成・Pagesを活用でき、旧URLを維持しやすい | HTMLからデータを抽出する変換器と回帰チェックが必要。状態管理は自作 | 低〜中。旧サイトを残し、代表コースだけ新画面へ | **推奨** |
| B. 静的データ＋小規模な新しいUI構成 | 画面の分割や比較機能を整理しやすい | ビルド・依存管理・リンク互換の検証が増える | 中。Leafletとデータは再利用 | AのUI複雑度が許容を超えた場合 |
| C. 大規模フレームワークへの全面移行 | 長期の画面拡張余地が大きい | 初期工数・移行回帰・運用変更が最大 | 高。旧単一HTMLの構造を置換 | 現段階では推奨しない |

**工数の概算:** 1人の実作業日、資料の入手・現地確認・レビューを含む。外部資料の不足や施設への確認待ちは含まない。P0監査3〜5日、P1データモデル・移行基盤5〜8日、P2代表3コースの調査・経路設計・レビュー12〜24日、P3画面・モーション・回帰10〜18日、合計**30〜55人日**。清澄白河の先行PoCはこの内訳で**5〜9人日程度**を目安にする。実際の初回1件の所要時間で再見積もりする。

**金額の見方:** 開発単価を仮に6万円／人日と置くと、30〜55人日は**約180〜330万円**。これは契約見積や市場価格ではなく、単価を置いた算数であり、撮影・写真権利処理・交通費・有料地図タイル・追加の現地調査は別。公開リポジトリでのGitHub Pages利用はプラン条件次第で基本ホスティング費を抑えられるが、現行アカウントのプラン・公開設定は未確認。タイル提供元の料金と想定閲覧量は`unknown`のままP0で確認する。

**外部サービスの扱い:** Leafletは現行1.9.4をまず維持する。Valhallaの公開デモは調査・事前計算時の公平な利用が前提で、公開サイトからの常時呼び出しを設計の土台にしない。現行の地理院タイルはウェブでのリアルタイム読込に出典表示の条件がある。CARTO Voyagerの現行案内はAPIキー付きの利用を案内しているが、既存のフォールバックURLにキーはないため、P0で継続利用条件と表示を確認する。OSM標準タイルへ変更する場合は、その表示帰属、キャッシュ、オフライン・一括取得の制限を守る。閲覧数が増える前にタイル提供先を選べる構成にする。

| リスク | 対応 |
|---|---|
| 旧97件の文章・線・距離が互いに違う | 移行時に3者を同じIDで突き合わせ、不一致は保留にする。旧データを上書きしない。 |
| APIや道路データの変化 | 生成日、エンジン、使用データを保存。再計算はレビューを通して採用する。 |
| 雨天の屋内経路や施設情報が古い | 施設の公式情報に確認日を付け、当日前の再確認項目を出す。 |
| モバイル地図の重さと通信不能 | 形状の遅延読み込み、地図なしの本文、テキスト旅程を用意する。タイルのオフライン一括保存は前提にしない。 |
| 見た目だけで現地安全と誤解される | `routed`／`map_reviewed`／`field_verified`を画面で区別し、未確認事項を表示する。 |
| 旧リンク切れと公開事故 | `course-*`対応表・旧URL回帰確認・公開元の確認をP0から行い、3件だけ段階公開する。 |

## 7. レビューで決める順序

1. 旧No.47を新しい1コースとして扱う範囲と、清澄白河の終点候補を調査で比較する方針。
2. 新A/B/C、旧A/B戦略、難易度、利用プロフィールを独立フィールドにするデータ契約。
3. 代表3コースに適用する検証状態と、現地確認が必要な範囲。
4. 公開設定・写真権利・タイル提供先をP0で確認した後のUI実装案A採否。
